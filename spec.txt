## 1. 项目定位

barelib 是一个**为 AI agent 设计、AI 可观测且 AI 可操作**的 2D 游戏引擎。

- 引擎侧：基于 raylib 深度精简的纯 2D 引擎（747 个公开 API），移除 3D / 着色器 / VR，
  全程程序化渲染与程序化音效，无美术堆料依赖。
- 智能侧：通过 AI Adapter 将运行中的游戏暴露为结构化 JSON 场景，并通过
  stdin/stdout 命令协议允许 AI 注入输入、控制游戏循环、录制回放、对比场景差异。

一句话定义：**让 AI 不仅"会写游戏代码"，更能"看见、操作、测试、修复"游戏本身。**

---

## 2. 背景与动机

### 2.1 问题

1. **趋势判断**：AI 制作游戏将同 AI 生图、生视频、生音乐一样成为常态。
   开发者用几句话描述玩法，在十几分钟到几十分钟内即可验证玩法是否好玩。
2. **前提条件**：剥离美术堆料——全程程序化渲染与程序化音效，使"好不好玩"
   从美术中抽离，聚焦纯玩法验证。
3. **现状痛点**：AI 进入商业引擎辅助开发存在根本性障碍——
   - AI 是"瞎"的：看不到运行结果，只能凭空生成代码，产出"看似完美实则处处有问题"的代码；
   - 修复低效：开发者用自然语言描述 bug，沟通带宽低，往往"描述半天修不好"。
4. **关键洞察**：AI 可以替代游戏测试员——而测试员是业界公认比程序员更难替代的岗位。
   AI 不知疲倦，可系统性扒光 bug，使游戏"无 bug 出炉"成为可能。

### 2.2 结论

与其让 AI 在一个它看不见的引擎里盲写代码，不如**给 AI 一个好用的引擎让它自己跑**：
看得见场景、动得了输入、能单帧调试、能录放复现——把 AI 从"代码生成器"
升级为完整开发闭环的参与者，从而进一步降低做游戏的成本。

## 3. 目标体系

### 3.1 使命

让"游戏制作"的门槛降低到与"用一句话画一张图"相当：
开发者描述玩法，AI 完成其余一切。

### 3.2 长期目标（Long-Term Goal）

将 barelib 建设为 **AI 原生游戏开发的事实标准底座**，使以下状态成为常态：

- **L1 闭环**：任何 AI agent 都能通过 barelib 协议在数分钟内理解并驱动一个 barelib 游戏，
  独立完成"编码 → 编译 → 运行 → 观测 → 测试 → 修复"的完整循环；
- **L2 体验**：开发者从"写代码"转为"描述意图"，玩法验证成本从数天降至十分钟级；
- **L3 质量**：AI 测试员成为质量保障的常规环节，AI 制作的游戏以
  "零已知缺陷"作为交付默认值；
- **L4 生态**：AI 协作工具链（自动测试、场景脚本、多 agent 协作、存量游戏接入）
  围绕 barelib 协议自然生长；
- **L5 精简**：引擎 API 面保持"少而精"——每个公开 API 必须高度实用，杜绝"为存在而存在"的接口；
  重复族（仅消除同构控制样板，如 Sound/Music/AudioStream 的 Play/Pause/Volume 等 21 个重复控制函数，但三结构本身是核心语义需保留）与低价值冷门函数持续收敛，新增 API 需论证必要性。

### 3.3 最终目标（Ultimate Goal）

> 一名开发者仅用自然语言描述玩法（几句话），在 **10–40 分钟**内获得一个
> AI 全程自主完成"编码 → 编译 → 运行 → 观测 → 测试 → 修复"闭环的、
> **可玩且经 AI 自主测试达到零已知缺陷**（无崩溃、无逻辑错误、无输入死角）
> 的 2D 程序化游戏原型。

### 3.4 成功衡量标准

| 维度 | 指标 | 当前基线 | 目标 |
|---|---|---|---|
| 可观测性 | 场景 JSON 描述延迟 | 3.3 ms @1024 元素满负荷（Debug 实测基线 2026-08，复现需同配置，非断言） | ≤ 1 帧（16ms），不拖慢游戏 ✅ 达标（基线 3.3ms < 16ms） |
| 可观测性 | 场景元素容量 | 硬编码上限，溢出静默丢弃 | 可配置，溢出给出明确错误而非静默截断 ✅ 已实现（`MAX_AI_ELEMENTS` 可覆盖 + JSON `overflow` 字段） |
| 闭环效率 | 自然语言 → 可玩原型耗时 | 未测定 | 10–40 分钟（P50，源自 §2.1） |
| 闭环效率 | 单轮 bug 修复（看→改→验） | 未测定 | < 5 分钟 |
| 质量 | 无窗口单元测试通过率 | test_ai_adapter 190 项断言 100% 通过 | 持续 100%，随能力扩展同步增长 |
| 协议 | 命令集稳定性 | 1.0（已版本化：`AI_PROTOCOL_VERSION` + JSON `protocol` 字段） | 版本化且向后兼容 |
| 采纳 | 外部游戏 / 工具接入数 | 0 | 形成可演示的第三方案例 |
| 精简 | 公开 API 实用度 | 747 个公开 API（2026-11 实测：引擎 672 + AI 层 75） | 每个公开 API 高度实用：变体族/重复族/冷门函数经盘点清单收敛（M4），新 API 需论证必要性，禁止无论证新增 |
| 精简 | 全部函数量（含内部 static，Windows 实际编译集，固定统计口径） | 949（2026-08：删 platform_web.c 后） | **必须小于原版全部函数量**（原版 ≥1200：公开 922 + rmodels 166 + 各 .c static；本 fork 因删 3D/Shader/精灵而必然更小）——函数量超标即视为"垃圾阻塞"，需盘点清除 |

> 注：标注"未测定"的闭环效率指标（自然语言→原型、单轮修复）需在端到端闭环演示中建立基准，当前仍为开放指标；其余指标已实测达标。

## 4. 范围

### 4.1 范围内（In Scope）

- 纯 2D 绘制：图形、纹理、文本、Camera2D、RenderTexture；
- 输入：键盘、鼠标、游戏手柄、触屏；输入注入（AI 侧）；
- 音频：Sound / Music / AudioStream（文件播放主路径）+ 程序化音效兜底（`AIPlayTone` / `AIPlayNoise`，5 种波形，**Sound 静态缓冲实现**）；
- AI 可观测性：`AIDrawXXX` 包装函数 + 手动注册 → 场景 JSON；非侵入自动捕获（`AISetAutoSceneCapture`，原生 `DrawXXX` 经引擎观察钩子）；
- AI 可操作性：stdin 命令循环、单帧步进、暂停/恢复、录制回放、快照 diff；
- 无窗口可测性：`AIDeps` 依赖注入 + 纯 CPU 单元测试；
- 中文开箱即用：内嵌 CJK 字体（GB2312 全覆盖）；
- 平台：**仅 Windows 编写、构建与运行**（工具链/开发/运行环境为 Windows 桌面）；**Web 与 Android 后端均已删除**（`platform_web.c` 于 M4 清理，`platform_android.c` 于提交前清理），非 Windows 代码不再保留。定位依据：普通开发者不会用 Linux 玩游戏，macOS 用户也不会选择这类 AI 工具；Web/桌面-Linux/Android 不在支持范围。

### 4.2 范围外（Out of Scope）

- 一切 3D：模型、材质、骨骼动画、相机3D、VR；
- GPU 可编程：着色器 API、后处理、计算着色器、SSBO；
- 外部 AI 运行时或网络依赖（AI Adapter 只产生数据，不连接任何 AI 服务）；
- 编辑器 / 可视化 IDE（如需要，作为生态工具另行规划）。

## 5. 核心设计原则

- **P1 可观测性优先**：引擎向 AI 暴露的是结构化数据（JSON），而非图像——AI 读取成本最低。
- **P2 可操作性对称**：AI 能读到的状态，都必须能通过协议操作（输入、步进、录放）。
- **P3 无窗口可测**：核心逻辑不依赖窗口与 GPU，`AIDeps` 注入即测。
- **P4 程序化内容**：渲染与音效程序化生成，剥离美术依赖，聚焦玩法。
- **P5 零外部依赖**：构建期无第三方依赖，运行期仅系统 API。
- **P6 简洁优先**：2D 能力优先，API 精简（747 个），变体函数可合并处保持克制。
- **P7 仅 exe 静态编译**：引擎只编译为可执行文件（exe），**不产出 DLL**。代码与构建围绕 exe 的静态链接展开——`RLAPI`/`RMAPI` 恒为空宏（无 import/export 标记），构建系统强制静态库（`add_library(... STATIC ...)`），`compile_game.bat` 无 DLL 拷贝步骤。历史教训：早期 "dll + AI runtime 热重载" 架构是错误方向，已废弃；一切功能（含程序化音频、AI 适配）都必须能在单个静态编译的 exe 内工作。

## 6. 系统能力规格

| 编号 | 能力 | 规格说明 |
|---|---|---|
| C1 | 场景观测 | `AIDrawXXX` 包装函数在绘制同时登记元素；`AIRegisterElement` 手动注册；非侵入自动捕获（`AISetAutoSceneCapture`，原生 `DrawXXX` 经引擎钩子登记，覆盖矩形/圆/文本族）；`AIGetSceneJSON()` 输出结构化 JSON（含屏幕尺寸、协议版本、元素类型/位置/尺寸/颜色、overflow/truncated） |
| C2 | 命令循环 | stdin 驱动，命令经线程读取入队，`AIUpdate()` 处理；支持场景、输入、循环控制、状态查询、录放、快照 diff 等命令（见 §7 命令表） |
| C3 | 输入注入 | `AIInjectInput()`：按键、鼠标点击/移动/滚轮、文本输入；Windows 实现基于 `SendInput`（`raylib_ai_input_win32.c`）；非 Windows 平台不在支持范围 |
| C4 | 录制回放 | `record` / `playback`：记录输入动作序列（含帧号），按帧重放，用于 bug 复现 |
| C5 | 快照与差异 | `snapshot` / `diff`：保存场景快照，对比当前帧输出变化（type/pos/size/radius/color），用于变化检测 |
| C6 | 日志拦截 | 捕获 raylib TraceLog 输出并附加时间戳，经 `errors` 命令暴露 |
| C7 | 程序化音频（兜底） | `AIPlayTone` / `AIPlayNoise`：sine/square/triangle/sawtooth/noise 5 种波形，含淡入淡出与 handle 控制。**实现：Sound 静态缓冲**（每次调用生成 PCM → `LoadSoundFromWave` → `PlaySound`，播完即止）。设计定位：零素材兜底——文件播放是主路径（AI 生成 WAV → `LoadSoundFromFile`），合成器用于原型验证阶段无素材时即时出声。修复记录：早期用 looping 流式 AudioStream + 单次喂数据导致回调无限回绕卡死音频线程（"一声后静音"），改 Sound 根治 |
| C8 | 后端状态查询 | 窗口 / 输入 / 时间 / 音频状态以 JSON 输出（`AIGetWindowStateJSON` 等） |
| C9 | 依赖注入 | `AIDeps` 表注入 mock 实现，使 AI Adapter 可在无窗口环境下测试与运行 |

## 7. 协议契约（AI ↔ 引擎）

- **传输**：stdin/stdout 行协议；无网络，无外部 AI 运行时。
- **数据格式**：全部结构化输出为 JSON。

### 7.1 命令表

| 命令 | 作用 |
|---|---|
| `version` | 查询协议版本（`AI_PROTOCOL_VERSION`） |
| `inputmode <sendinput\|postmessage>` | 切换输入模拟模式（PostMessage 模式后台窗口可注入，spec R6） |
| `scene` | 获取当前场景 JSON |
| `input press <key>` / `click` / `move` / `scroll` / `type` | 注入输入 |
| `pause` / `resume` / `step <n>` | 控制游戏循环（单帧步进） |
| `state` | 查询窗口 / 输入 / 时间 / 音频后端状态 |
| `errors` | 输出捕获的日志与错误（带时间戳） |
| `elements` | 枚举已登记场景元素 |
| `record [stop]` / `playback` | 录制 / 回放输入序列 |
| `snapshot` / `diff` | 保存场景快照 / 对比当前帧 |
| `quiet` / `loud` | 切换自动场景输出（AI_OUTPUT_STDOUT 模式） |
| `help` / `quit` | 帮助 / 退出 |

### 7.2 输出标记

协议使用显式标记界定结构化输出：
- `<<AI_OK>> message` — 命令确认
- `<<AI_ERROR>> [code:N] message` — 命令错误（N = `AIErrorCode`）
- `<<AI_SCENE_BEGIN>>` / `<<AI_SCENE_END>>` — 场景 JSON 数据块
- `<<AI_DIFF_BEGIN>>` / `<<AI_DIFF_END>>` — 快照差异 JSON 数据块
- `<<AI_HELP>>` … `<<AI_HELP_END>>` — 帮助文本
- `<<AI_CRASH>>` … `<<AI_CRASH_END>>` — 退出时检测到 ERROR/FATAL 日志（stderr，仅真错误触发）
- `<<AI_SHUTDOWN>>` — 适配器关闭

供 AI 端可靠切分数据流（详见 `docs/ai_adapter.md`）。

## 8. 非功能要求

- **N1 性能**：AI 观测不得改变游戏语义；场景 JSON 生成不得拖慢主循环（目标 ≤ 1 帧）。
- **N2 容量**：场景元素缓冲上限可配置；溢出必须返回明确错误。
- **N3 平台范围**：编写、构建与使用该引擎的平台仅 Windows（桌面）；Web、Android 与 Linux/macOS 桌面构建均不设优先级、不设 CI、不提供保证。核心代码保持可移植书写（不引入 Windows-only 依赖到公共 API）。
- **N4 兼容性**：命令集与 JSON 字段变更必须版本化，保持向后兼容。
- **N5 测试纪律**：无窗口可测的功能必须有无窗口测试；变更不得降低 100% 通过率。

## 10. 风险与已知限制

- **R1 合作式可观测**：AI 只能看到 `AIDrawXXX` 登记过的元素；未配合包装函数的游戏对 AI 不可见。对 AI 自写游戏成立；**存量游戏已可用自动场景捕获**（`AISetAutoSceneCapture`：原生 `DrawXXX` 经引擎观察钩子自动登记，矩形/圆/文本三大绘制族已验证，零游戏改动）。剩余：lines/poly/texture 等绘制族 + 与 wrapper 的混用语义。
- **R2 设计问题的澄清依赖制作者的投入**：AI 测试员可穷尽"可枚举的状态问题"
  （崩溃、碰撞、越界）；对"需求误解、玩法失衡"等设计问题，AI 无法单方面给出
  最终判断，但制作者完全可以与 AI 测试员反复交流、**grilling（迭代质询）**，
  把模糊的需求逐条显式化为可测试的断言，从而同样逼近设计正确性——这正是本规格
  推崇的开发方式：制作者描述意图，AI 测试员以问题反馈驱动制作者把需求说清楚。
  风险在于：澄清效果与制作者的投入成正比，若制作者跳过质询环节直接交付，
  "无 bug 出炉"仍只保证状态正确性，不保证设计正确性。
- **R3 上游脱节**：深度 fork 与 raylib 主线同步成本高，需持续人工合并，避免安全与功能滞后。
- **R4 仓库卫生**（已闭环）：构建产物曾大量入库（已清理，含根目录残留 `ai_game_template.exe`）；`.gitignore` 覆盖 `*.exe`/`*.dll`/`obj/`，CI（`build_cmake.yml` 新增 `Repo hygiene` 步骤）检查跟踪的构建产物，违规即失败。
- **R5 AIClose 命令线程关闭竞态**：stdin 读取线程阻塞在 `fgets` 时无法强制退出。已加固（M2 内完成）：`AIClose` 等待超时后改为 **detach 线程 + 延迟释放 adapter/mutex 至进程退出**，消除 use-after-free；代价是极端场景下 adapter 内存延迟回收（进程退出时由 OS 回收）。完整修复（stdin 关闭机制或线程取消协议）仍属线程模型改造，留待后续。
- **R6 键注入依赖前台窗口**（已解决）：`AIInjectInput` 的按键注入原基于 `SendInput`，要求游戏窗口处于前台（系统级约束），后台窗口收不到键盘事件。已实现 **PostMessage 注入模式**（`inputmode postmessage` 命令 / `AISetInputMode`）：直接向游戏窗口投递 WM_* 消息，后台窗口同样可操作（AI 测试员可无人值守驱动游戏）；修复了扩展键 lParam 需 KF_EXTENDED 位、key-up 需 transition state（bit 31）两个细节，并让 press 的 up 延迟一帧投递（跨帧，IsKeyPressed 可检测）。默认仍为 SendInput 以保持兼容。

## 附录 A：作者原语（未修改，原文照录）

> barelib是为ai agent专门适配的游戏引擎，我觉得未来开发者肯定想让ai做游戏，就像现在ai生图，生视频音乐那样，几句话，十几分钟到几十分钟就能让开发者快速验证自己想要的玩法，剥离美术堆料，全程采用程序化渲染与程序化音效，是否真正好玩，现在的ai进入商业游戏引擎，辅助做游戏存在大量问题，比如ai是瞎的，会生成看似完美实则处处有问题的代码，跟它描述半天bug都修不好，所以我造了这个引擎，我给ai一个好用的引擎让它自己跑，进一步降低做游戏的成本，ai能"看"到bug，ai能模拟输入做游戏测试员，使用体验上更加流畅舒适。
>
> 当时我发现ai可以替代人类做游戏测试员时，我就感觉自己做的引擎有点超出预期，有点超模了这个引擎的专属功能，毕竟游戏测试员，找bug的被现代默认是比程序员要难替代得多的人，有了这个，ai可不会累，扒光所有bug，用它制作的游戏，只要想，成品就可以无bug出炉。
